01 What this actually is

The name and README are misleading. Here is the truth, verified against the code and git.

MyNilam (also branded "Rentel" internally) is a real-estate and hostel/PG management platform — think "list a flat/house/commercial space for rent or sale" combined with a dedicated hostel & co-living management system (rooms, beds, occupancy, vacancies).

It is a pnpm + Turborepo monorepo containing:

  • apps/web — the customer-facing Next.js 14 web app (browse/search properties, hostels, post ads, inquiries, reviews, favorites, dashboard).
  • apps/django-backend — the real REST API (Django 5.2 + Django REST Framework + SimpleJWT).
  • apps/mobile — an Expo / React Native stub (a single "Mobile coming soon..." screen).
  • packages/shared — a TypeScript SDK: shared types + an axios API client + mock data.
⚠️
The repo is named "MyNilam-Django" but the default main branch is frontend-only. The full-stack reality (Django backend) lives on the staging branch. The README.md also documents an Express/Prisma backend and a prod branch — neither exists. Always trust git branch -a and the source, not the README.

The base model — CommonModel (soft delete)

Every model extends core.models.CommonModel, which adds:

  • row_guid — a UUID (unique)
  • is_active / is_deleted — soft-delete flags
  • created_at / updated_at / created_by / modified_by — audit timestamps & authors
🔑
BaseModelManager.get_queryset() auto-filters to is_deleted=False, is_active=True. So a "deleted" row silently disappears from normal ORM queries — deleting data is done by flipping flags, never .delete() in app code.

The Property model (the heart of the domain)

A property is a full listing: owner, title/description, a geo location chain (country → state → district → city → area → locality), address fields, lat/lng, bedrooms/bathrooms/area, furnishing status, listing_purpose (Rent/Sale), price + currency + rent frequency, security deposit, availability dates, lease durations, listing_status (Draft/Active/Pending/Rented/Sold/Expired/Suspended), verification_status (Pending/Verified/Rejected), featured flag, and a view counter. It also has indexes on (city, area), (listing_status, available_from), owner, and (lat, lng).

For hostels, a HostelConfig is a 1:1 extension of a Property (capacity, gender policy, facilities, vacant beds/rooms, pricing) which fans out into HostelRoom → HostelBed (bed-level occupancy with a status of Vacant/Occupied/Reserved/Maintenance and an assigned tenant).

05 Data model highlights

User (accounts.User)
Custom AbstractBaseUser — email is the username (no username field). Extra fields: phone_number, profile_image_url, date_of_birth, nationality_country, preferred_language, email_verified, phone_verified, failed_login_attempts, account_locked_until, two_factor_enabled / two_factor_secret.
RBAC (accounts)
Role ↔ UserRole (m2m to User, unique together) and Role ↔ RolePermission (m2m to Permission). Permissions have a module field. JWT embeds roles and permissions claims.
Session (accounts.UserSession)
Tracks an active login: refresh_token_hash (SHA-256 of the refresh token), device_info, ip_address, expires_at, is_revoked. This is the linchpin of the custom auth (see §6).
Hostel domain
HostelConfig (1:1 Property) → HostelRoom (room number, floor, sharing type 1/2/3/4/dorm, monthly rate, AC, attached bathroom) → HostelBed (bed name, status, assigned tenant, check-in/out). Photos categorized (cover/entrance/room/bathroom/dining/common area).
Leases
LeaseApplication (submitted → approved/rejected) → LeaseContract (tenant/landlord, dates, rent, escalation, termination) → LeasePayment + LeaseInvoice (billing periods, tax, PDF URL).
Communications
Conversation (typed: General/LeaseInquiry/MaintenanceUpdate/…) → Message (Text/Image/File/System). Plus Inquiry, Review (1–5 star, moderation status), Favorite, SavedSearch, Notification (multi-channel).

06 Auth & RBAC — the most important thing to understand

This project's authentication is custom and strict. Get this wrong and every valid token will 401.

Five roles

RoleScope
guestUnauthenticated browsing / search.
normalRegistered user — browse, post ads, inquire, review, favorite.
hostel_adminHostel owner — manages their hostel's dashboard (rooms, beds, bookings).
employeeStaff/moderator — view listings, verify ads, moderate reviews.
super_adminPlatform owner — unrestricted.

Token scheme

  • Access token — 15 min lifetime, stored in localStorage, sent as Authorization: Bearer ….
  • Refresh token — 7 days, rotating + blacklisted, stored in an httpOnly cookie scoped to /api/auth/.
  • SIMPLE_JWT uses HS256, TOKEN_OBTAIN_SERIALIZER = accounts.api.serializers.CustomTokenObtainPairSerializer.

The fail-closed session guard (core/jwt.py)

🔒
CustomJWTAuthentication rejects a request unless the user has at least one non-revoked UserSession row. Consequences:
  • Login MUST create a UserSession (the login serializer does this automatically).
  • Logout MUST revoke it (set is_revoked=True), or the token stays valid.
  • Deleting/deactivating a user also invalidates auth (is_active/is_deleted checked).

Login flow (serializer)

On POST /api/auth/login/, the serializer: checks account lockout → validates credentials → on failure increments failed_login_attempts (5 fails = 15-min lock) and writes an AuditLog → on success resets the counter, checks 2FA (returns mfa_required), hashes the refresh token, creates a UserSession, and logs UserLogin.

Permission classes

accounts/api/permissions.py defines IsSuperAdmin and IsHostelAdmin, both of which check user.user_roles.filter(role__name=…) (superuser always passes). The DRF default permission is IsAuthenticated — so nearly every endpoint requires a logged-in user unless overridden.

08 Frontend architecture (Next.js App Router)

The PageModel pattern (the ONE convention everything follows)

Every page splits into two files: a view (page.tsx, pure JSX) and a logic hook (XxxPageModel.ts, all state + side-effects).

app/
├── page.tsx + HomepageModel.ts        # home
├── login/page.tsx + LoginPageModel.ts
├── signup/page.tsx + SignupPageModel.ts
├── post/page.tsx + PostPageModel.ts   # "post an ad"
├── dashboard/page.tsx + DashboardPageModel.ts
├── settings/page.tsx + SettingsPageModel.ts
├── properties/[id]/page.tsx           # detail page
├── hooks/                             # data layer (React Query)
│   ├── use-auth.ts  use-properties.ts  use-conversations.ts
│   ├── use-favorites.ts  use-hostel-config.ts  use-inquiries.ts
│   └── use-reviews.ts  use-visits.ts
└── providers/query-provider.tsx       # TanStack QueryClient

Example: useHomepageModel() owns filters, sort, view type (grid/list/map), and the active tab (Properties vs Hostels), and consumes useProperties(filters) + useAuth(). It also does client-side auth guarding — redirect to /login if no user, or to /dashboard if the user is hostel_admin.

Mock vs real data switch

The shared ApiClient reads NEXT_PUBLIC_USE_MOCK (web) / EXPO_PUBLIC_USE_MOCK (mobile).

When USE_MOCK=true, the SDK serves mock-data.ts (localStorage-persisted) and no backend is needed. When false, all calls hit Django. Note: client.ts defaults to false (real API) if the flag is unset.

Other frontend details

  • The dashboard is role-aware with tabs — my-ads, verify-users, employees, users-list, hostel-manage — rendered per the logged-in role.
  • Heavy use of glassmorphism / dark-mode styling (Tailwind + next-themes, a ThemeToggle in the header).
  • PropertyMap (Leaflet) is loaded with next/dynamic(…, { ssr: false }) to avoid SSR issues.
  • Header/Footer live in components/layout/; reusable primitives in components/ui/ (button, card, input, badge, textarea, city-autocomplete, empty-state).

10 Field-naming gap (frontend vs backend)

The frontend's TypeScript types and the Django model fields do not line up. This is the #1 source of "why is my data null" bugs.

Frontend (shared types)Django Property model
listing_type (sale/rent/roommate)listing_purpose (Sale/Rent)
status, is_publishedlisting_status (Draft/Active/Pending/Rented/Sold/Expired/Suspended)
is_furnished (bool)furnishing_status (Furnished/Semi-Furnished/Unfurnished)
⚠️
The input serializer PropertyCreateSerializer explicitly maps the frontend names to model fields (e.g. listing_type → listing_purpose, is_furnished → furnishing_status). Always verify the mapping in properties/api/serializers.py before wiring a new real API call — don't assume the mock type shapes match Django.

11 Deployment & environments

Frontend → Vercel
Standard Next.js deploy with Vercel's native pnpm monorepo detection (no vercel.json; it was removed in favor of Vercel Project UI settings).
Backend → Render
render.yaml declares a Python web service rooted at apps/django-backend. build.sh runs pip install -r requirements.txt + collectstatic + migrate; start command is gunicorn Project.wsgi:application.

CORS / CSRF

CORS_ALLOWED_ORIGINS and CSRF_TRUSTED_ORIGINS allow localhost:3000, 127.0.0.1:3000, and my-nilam-django-web.vercel.app; a regex also allows *.vercel.app. CORS_ALLOW_CREDENTIALS = True (needed for the refresh cookie).

14 Gotchas & things to watch

  1. Repo name lies. "MyNilam-Django" has zero Django on main; the real backend is on staging. The README's Express backend + prod branch don't exist.
  2. Fail-closed auth. A valid JWT still 401s if there's no active UserSession row. Login creates it, logout must revoke it.
  3. Soft delete is automatic. CommonModel's manager hides is_deleted/is_active rows from normal queries.
  4. Field-name mismatch between frontend types and Django fields (see §10) — verify serializers before wiring calls.
  5. Access token in localStorage (XSS-exposed by design here) while the refresh token is in an httpOnly cookie — a deliberate split.
  6. Redis / Celery / Channels are listed but not active — don't assume async tasks work yet.
  7. Mobile app is a stub — a single "coming soon" screen; no real screens yet.
  8. CI is a placeholder — no automated tests/checks run on push.
  9. Minor dead code — e.g. layout.tsx imports globals.css twice, and mock types don't fully match backend fields.
  10. Team rule (.agents/AGENTS.md): keep a single task operation ≤ 1 min, and check background command status every 20s.
